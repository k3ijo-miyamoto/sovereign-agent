## 総括・所見

5タスク・15モデルの評価を通じて、以下の判断が導けるようになった。

### 所見1: 実用に耐えるモデルは5つに絞られる

全タスクで安定して動くのは **gemma3:27b / gemma3:12b / qwen3:14b / qwen3:8b / qwen3:8b-nothink** の5モデルのみ。これ以外のモデルは少なくとも1タスクで stab=0% または T1 以下に落ちており、本番ルーティングには不向きである。

→ **判断**: ソブリンAIの実運用モデルはこの5つから選ぶ。

### 所見2: コスト最適解は gemma3:12b

フェーズ0（バグ修正）では27bが上位だったが、フェーズ1（実務4タスク）では12bが全ケースで27bと同等スコア・同効率を維持した。モデルサイズが半分＝VRAMと推論速度のコストが実質半減する。

→ **判断**: 精度よりコスト・速度を優先する場合、12bに切り替えてよい。ただしバグ修正の複雑ケース（boundary_bug）では27bが有利であるため、タスク種別で切り替えることが最適。

### 所見3: 「docstringだけ苦手」なモデルは使い道がある

codestral:22b・qwen2.5-coder:14b・deepseek-coder-v2:16b はdocstringで失敗したが、テスト生成・型アノテーションでは T3 を達成した。失敗の原因は「既存コードを変えるな」という制約への対応が苦手なことにあり、新しいコードを書くタスクでは機能する。

→ **判断**: これらを「汎用モデル」として使うのは不適切。ただし「テスト生成専用」として限定的に使うオプションはある。コストを落としたい場面での補助的な選択肢。

### 所見4: phi4:14b は本番に使えない

docstringは書けるが、テスト生成ではpytest が全回失敗（stab=0%）。「動いているように見えるが出力が壊れている」という最も扱いにくい失敗パターンを示す。タスクによってstabが0%↔100%と激しく振れ、予測可能性が低い。

→ **判断**: 採用しない。

### 所見5: docstringのエッジケース漏れはプロンプトで解決できる（ただし副作用あり）

Case02（引数5つの複雑な関数）では、Tier1全モデルが T2 止まりで「空リスト入力への言及」を省略していた。「空リストの場合も必ず説明せよ」を1行追加したCase02b（プロンプト実験）の結果：

| 結果 | モデル |
|---|---|
| T3 達成（改善）| gemma3:27b / 12b / qwen3:14b / 8b / 8b-nothink / qwen2.5-coder:14b |
| 変化なし・悪化 | devstral:24b（T2→**T1崩壊**）/ phi4（本体変更）/ mistral-nemo（本体変更）|
| 不変 | codestral / granite / llama / qwen2.5:7b |

Tier1の5モデルは全員 T3 突破。モデルは空リストの挙動を理解しており、「求められていないから書かなかった」だけだった。

**devstral:24b の崩壊が最大の発見。** プロンプト1行の追加でdocstringを書かなくなった（T2→T1）。Tier1に分類していたが、プロンプト感度の高さが本番運用上のリスクを示している。

→ **判断（所見5を更新）**: Tier1でのプロンプト設計次第でT3は達成できる。「明示的に求めたことしか書かない」という特性を踏まえ、プロンプトでカバレッジを指定する設計が有効。devstral:24b はTier1から除外し、プロンプト感度の高い不安定モデルとして扱う。

## 概要

フェーズ0の全15モデルを対象に、実務タスクを評価した。

- **対象モデル**: 15モデル（全フェーズ0対象）
- **評価ケース**: docstring生成（01・02・02b）、ユニットテスト生成（03）、型アノテーション追加（04）、コミットメッセージ生成（05）
- **02b はプロンプト実験**: Case02のprompt.txtに1行追記し、mentions_empty の改善を検証
- **runs**: 各3回（安定性測定）

## ケース概要

### 01_docstring_generate（単純）
- 対象: `normalize_scores(scores)` — min-max正規化
- 引数1つ、エッジケース2つ（空リスト・全同値）
- T3条件: 空リストと全同値ケースへの言及

### 02_docstring_complex（複雑）
- 対象: `compute_moving_average(values, window, min_periods, pad_value, weights)`
- 引数5つ（デフォルト値あり）、エッジケース7つ以上
- T3条件: 空リスト・min_periods挙動・weights・pad_valueへの言及

### 03_test_generate（ユニットテスト生成）
- 対象: `chunk(lst, size)` — リストをsize個ずつに分割
- 新規ファイル（test_target.py）を作成し pytest で自動実行
- T2条件: pytest exit 0（完全客観的）
- T3条件: T2 + ValueError テスト + 空リストテスト

### 02b_docstring_complex（プロンプト実験）
- Case02と同一の target.py・expected_criteria.json
- prompt.txt に「空リストの場合も必ず説明せよ」を1行追記
- 目的: mentions_empty の失敗がプロンプト起因か・モデル能力限界かを判別

### 04_type_annotate（型アノテーション追加）
- 対象: `parse_csv_row` / `count_words` / `clamp` の3関数
- 関数本体を変えずに引数・戻り値の型ヒントを追加する
- T2条件: 本体変更なし + 戻り値アノテーション（`->`）あり
- T3条件: T2 + 全関数・全引数・全戻り値を完全アノテート

### 05_commit_message（コミットメッセージ生成）
- 入力: `target_diff.txt`（git diff — `compute_moving_average` への `weights` パラメータ追加）
- 出力: `commit_message.txt`（モデルが生成）
- T1条件: ファイルが生成されている
- T2条件: T1 + 変更の種類を示す動詞 + 変更対象（weighted/関数名）への言及
- T3条件: T2 + subject行が72文字以内 + weightsパラメータへの言及

## 考察

### 1. docstring生成は「qwen3ファミリーが制圧」

qwen3:8b（5GB）がgemma3:27b（17GB）と同スコア・同効率を達成。「docstring生成は軽量モデルで十分」の仮説が強く支持された。qwen3はサイズに関係なく安定しており、ネイティブtools APIの恩恵が大きいと考えられる。

### 2. gemma3:12b が27bと完全同等

gemma3:12bがcalls=2.0・stab=100%・スコア同等を達成。フェーズ0ではgemma3:27bが上位だったが、docstringタスクでは12bで代替できる。コスト半減の大きな知見。

### 3. 「コード特化モデル」がdocstringタスクで逆に弱い

| モデル | 性質 | Case02 calls | Case02 stab |
|---|---|:---:|:---:|
| qwen2.5-coder:14b | コード特化 | 11.0 | 33% |
| deepseek-coder-v2:16b | コード特化 | 14.7 | 0% |
| qwen3:14b | 汎用 | 2.0 | 100% |

コード補完に特化した訓練が「コードを書かず docstring のみ追加せよ」という制約に干渉している可能性がある。"Do not change the function body" という指示を無視して本体を変更してしまう傾向が顕著。

### 4. granite3.3:8b の calls=54.3 は異常

case01 で平均54.3回のツール呼び出し。3回のうち少なくとも1回がタイムアウト寸前まで試行し続けたと推測される。docstring を追加できずに「書いては消す」ループに陥った可能性が高い。

### 5. llama3.1:8b は XML モード非互換

case01 で `syntax_valid` が❌（Pythonとして構文エラー）。XML tool call フォーマットの解釈に失敗し、XMLタグをコードに混入させたと思われる。

### 6. `mentions_empty` は全モデルが case02 でゼロ

引数5つの複雑な関数では、weights/pad_value/min_periodsの説明に注力し「空リストを返す」という入力エッジケースへの言及が全モデルで省略された。ケース01（単純）では Tier1 全モデルが通過しており、**引数の多さが注意資源を奪う**という仮説を支持する。

### 7. `mentions_weights_alignment` は全モデル失敗（ボーナス指標として継続）

`weights[window - len(chunk):]` という右寄せアライメントへの言及はゼロ。コードを深く読まないと気づけない非自明な挙動であり、現状モデルの限界を示す良い指標。T3スコアリングからは除外済みで正解。
